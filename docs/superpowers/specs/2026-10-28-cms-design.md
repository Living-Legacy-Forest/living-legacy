# Living Legacy Forest CMS: design spec

Date: 2026-10-28
Status: approved; milestone 1 (foundation) built

## 1. Goal

A custom, WordPress-style CMS for the Living Legacy Forest marketing site, so
non-technical staff can write and publish blog posts and supporting content
without a developer or a redeploy. The public site is still in design and will
be built later as a separate app that reads the same database.

**Success criteria**

- An editor who has used WordPress can write, publish, edit and trash a post
  without training.
- Every content change is reversible (drafts, revisions, trash).
- The future public site can query published content with typed helpers and
  no API layer.

## 2. Scope

**In v1**

- Blog: posts, categories, tags, featured images, authors, SEO fields
- Media library
- FAQs (grouped), testimonials, team members
- Site settings, 301 redirects manager
- Users with Admin and Editor roles, Google sign-in
- Drafts, publish/unpublish, scheduled publishing, revision history, trash

**Not in v1**

- Public website and its page builder (after design is approved)
- Forests/locations and packages content types
- Approval workflow
- Comments, multi-language, plugins/themes
- WordPress content import (planned as the first follow-up, see section 12)

## 3. Tooling

- **Bun** as package manager (Bun workspaces), script runner and local tooling.
  Production code runs on Cloudflare Workers (workerd), not Bun, so app code
  must stick to Web/Workers APIs and avoid `Bun.*` APIs.
- TanStack Start, React, TypeScript (strict), Tailwind v4, shadcn/ui
- editorcn (Tiptap-based, installed from the shadcn registry) for rich text
- Drizzle ORM + drizzle-kit, Cloudflare D1, Cloudflare R2
- Better Auth (Drizzle adapter on D1) with Google OAuth
- Zod for all content schemas
- Vitest with `@cloudflare/vitest-pool-workers`, Playwright for end-to-end tests
- ESLint and Prettier for lint and format (the repo's existing setup)
- Git, trunk-based, Conventional Commits

## 4. Architecture

```
living-legacy/                 Bun workspace
├── apps/
│   ├── cms/                   TanStack Start → Worker "llf-cms" (admin UI)
│   └── web/                   existing Astro site; moves from Sanity to D1 later
├── packages/
│   ├── db/                    Drizzle schema, migrations, typed queries
│   └── content/               Zod schemas per content type, shared rules
└── each app has its own wrangler config, bound to the same D1 and R2
```

- The CMS uses TanStack Start server functions for every read and write. There
  is no public HTTP API.
- `packages/db` exports read helpers the public site will use
  (`getPublishedPostBySlug`, `listPublishedPosts`, `listFaqs`, ...). They only
  ever return published, non-trashed content.
- `packages/content` holds the Zod schemas used by admin forms (client) and
  server functions (server), so validation is identical on both sides.
- Environments: local (wrangler local D1/R2), staging, production. Each has its
  own D1 database and R2 bucket. Migrations are generated by drizzle-kit and
  applied with `wrangler d1 migrations apply`.
- Every publish, unpublish, trash or settings change writes a row to
  `publish_events`. The public site will use this later to purge its edge cache.
  The CMS does not know about the site.

## 5. Data model

IDs are ULIDs (text). Timestamps are integer milliseconds.

### Shared lifecycle fields (posts, faqs, testimonials, team_members)

| Field | Purpose |
|---|---|
| `status` | `draft` or `published` |
| `draft` | JSON of pending changes to a published item, or null |
| `published_at` | First publish time (editable "post date" for posts) |
| `updated_at` | Also used as the version for conflict detection |
| `deleted_at` | Set when trashed, null otherwise |
| `created_by`, `updated_by` | User IDs |

**Rules**

- Typed columns always hold the live version. The site reads
  `status = 'published' AND deleted_at IS NULL`.
- A never-published item is `status = draft` and its typed columns hold the
  working copy.
- Editing a published item writes to `draft`. The live version is untouched
  until **Update** is pressed.
- **Publish/Update** copies the draft into columns, clears `draft`, writes a
  `revisions` snapshot and a `publish_events` row.
- **Discard changes** clears `draft`.
- **Restore revision** loads the snapshot into `draft` for review, then the user
  presses Update.
- **Unpublish** sets `status = draft`.
- **Trash** sets `deleted_at` (and unpublishes). **Restore** clears it.
  **Delete permanently** removes the row and its revisions (Admin only). Trash
  older than 30 days is purged by a daily cron trigger.

**Scheduling**

- A draft can be scheduled (`posts.scheduled_at`); it stays a draft until then.
- A cron trigger (every 5 minutes) publishes due drafts through the same
  publish path as the Publish button: revision, publish event and redirects.
- Scheduling, publishing, unscheduling or trashing clears `scheduled_at`.
- Times are picked and shown in Melbourne time (AEST/AEDT).

### Content tables

- **posts**: title, slug (unique among non-trashed), excerpt, body (Tiptap
  JSON), featured_media_id, author_id → team_members, seo_title,
  seo_description, og_media_id, noindex
- **terms**: type (`category` or `tag`), name, slug (unique per type),
  description, parent_id (categories only, one level)
- **post_terms**: post_id, term_id (many to many, like WordPress)
- **faq_groups**: name, sort_order
- **faqs**: question, answer (Tiptap JSON), group_id, sort_order
- **testimonials**: quote, name, relationship, location, photo_media_id,
  featured
- **team_members**: name, role, bio, photo_media_id, sort_order. Also the blog
  author list.

Terms, FAQ groups, settings and redirects are live on save (no draft state).

### Other tables

- **site_settings**: single row, JSON validated by Zod: site name, contact
  details, footer text, legal entity and ABN, patent numbers, social links,
  default SEO and OG image.
- **redirects**: from_path (unique), to_path, status_code (301 or 302), hits,
  note. Changing the slug of a published post creates a 301 automatically.
- **media**: r2_key, filename, mime, size, width, height, alt, caption,
  uploaded_by, created_at
- **revisions**: entity_type, entity_id, snapshot JSON, created_by, created_at
- **publish_events**: entity_type, entity_id, action, paths affected, created_at
- **Better Auth tables**: user (plus `role`: `admin` or `editor`), session,
  account, verification

## 6. Admin UX (modelled on WordPress)

### Layout

Left sidebar, collapsible, mobile drawer:

- Dashboard
- Posts: All posts, Add new, Categories, Tags
- Media
- FAQs, Testimonials, Team
- Redirects, Users, Settings (Admin only)

Top bar: site name, "View site" (once the site exists), user menu.

### Dashboard

Counts at a glance (published posts, drafts, media), "Your recent drafts",
"Recently published", and a quick-draft card (title + text, saves a draft).

### All posts

- Status tabs with counts: All | Published | Drafts | Trash
- Search by title; filters for category, tag, author and month
- Columns: title, author, categories, tags, date, status; sortable by title and
  date
- Row actions: Edit, Preview, Duplicate, Trash (Trash tab: Restore, Delete
  permanently)
- Bulk actions: Publish, Move to draft, Trash, Restore, Delete permanently
- 20 per page, paginated; filters kept in the URL

### Post editor

Two-column layout like the WordPress editor.

**Main column**

- Title (large input)
- Permalink under the title, auto-generated from the title until the first
  publish, editable
- Body: editorcn block editor (headings, paragraphs, lists, quotes, links,
  images from the media library, embeds, tables, dividers)
- Excerpt

**Sidebar panels**

- **Publish**: status, post date, Save draft, Preview, Publish / Update,
  Discard changes, Unpublish, Move to trash, "Last saved" time
- **Categories**: checkbox tree, "Add new category" inline
- **Tags**: combobox, create new on Enter
- **Featured image**: media picker, alt text shown
- **Author**: team member select
- **SEO**: SEO title and description with character counters, Google snippet
  preview, OG image, noindex toggle
- **Revisions**: count and list; view a revision side by side with the current
  version, Restore

**Behaviour**

- Autosave every 10 seconds of inactivity into the draft (never touches the live
  version).
- A warning appears when leaving with unsaved changes.
- Preview: `/preview/posts/:id` inside the CMS renders the draft with neutral
  prose styling. When the public site exists it will offer a signed-token
  preview instead.

### Media library

- Grid and list views, search, filter by type and month
- Drag-and-drop multi-upload with progress
- Accepted: JPEG, PNG, WebP, AVIF, GIF, PDF; max 20 MB. SVG is rejected (XSS
  risk).
- Details panel: preview, alt text, caption, dimensions, URL copy, "Used in"
  list
- Alt text is required before an image can be inserted into content
- Deleting media that is in use is blocked, and the list of uses is shown

### FAQs, testimonials, team

Simple list + form screens with the same Publish panel. FAQs and team support
drag-to-reorder.

### Redirects, Users, Settings

- **Redirects**: table with add/edit/delete, hit counts, CSV import (for the
  WordPress migration)
- **Users**: invite by email with a role, change role, remove
- **Settings**: one form grouped into sections

## 7. Auth and roles

- Better Auth with Google sign-in. Sessions are stored in D1.
- Invite-only: sign-in succeeds only for emails an Admin has added. The first
  Admin is created from the `BOOTSTRAP_ADMIN_EMAILS` environment variable.
- **Editor**: posts, terms, media, FAQs, testimonials, team; publish, trash and
  restore.
- **Admin**: everything an Editor can do plus users, settings, redirects and
  permanent delete.
- Every server function runs through an auth middleware that checks the session
  and role. The UI hides what a role cannot do, but the server enforces it.
- Optional extra layer: Cloudflare Access in front of the CMS hostname.

## 8. Media delivery

- Uploads go through a server function that checks size and MIME type (by
  sniffing the magic bytes, not trusting the extension) and streams the file to
  R2 under `media/YYYY/MM/<ulid>-<slug>.<ext>`.
- Width and height are read in the browser before upload and stored.
- Images are served from a `/media/*` route with Cloudflare Images
  transformations (`width`, `quality`, `format=auto`). This needs Images
  transformations enabled on the zone.
- Rich text stores media IDs in image nodes, so files can be resized or moved
  without rewriting content.

## 9. Error handling

- Zod errors map to individual form fields; server errors show as toasts.
- Optimistic concurrency: saves send `updated_at`. If someone else saved in the
  meantime, the server rejects the save and the editor shows "This post was
  changed by Name. Reload or overwrite?"
- Rich text JSON is validated against an allowlist of node and mark types
  before it is saved.
- Route error boundaries with a retry option; a 404 page for missing items.
- Workers logs and observability are enabled. Errors are logged with request ID
  and user ID.

## 10. Accessibility and quality

- shadcn/Radix primitives, fully keyboard operable, visible focus, WCAG 2.2 AA
  for the admin.
- Responsive down to phone width; editing on a phone works, but the editor is
  optimised for desktop.
- Light theme only: white and neutral greys. Charts are the only colour, from the website palette.

## 11. Testing

- **Unit/integration (Vitest + workers pool, real D1 in Miniflare)**: the
  draft/publish/revision/trash lifecycle, slug uniqueness and auto-redirect,
  role checks on every server function, upload validation, the read helpers
  return only published content.
- **End to end (Playwright, test-only auth bypass)**: sign in, create a post,
  add a category, tag and featured image, publish, edit, update, restore a
  revision, trash, restore.
- CI (GitHub Actions): typecheck, Biome, Vitest, Playwright on every push.
- A seed script loads sample posts, terms, FAQs and media for local dev.

## 12. Milestones

1. **Foundation**: Bun workspace, `packages/db` and `packages/content`,
   migrations, Better Auth with roles, admin shell (sidebar, dashboard
   placeholder), deploy to staging.
2. **Media library**: upload, R2, the `/media` transform route, library UI,
   picker component.
3. **Posts**: list screen, editor with editorcn, categories and tags, the
   draft/publish/revision/trash lifecycle, autosave, preview, SEO panel.
4. **Supporting content**: FAQs, testimonials, team.
5. **Admin tools**: settings, redirects (with CSV import), users and invites,
   the trash purge cron.
6. **Hardening**: complete the e2e suite, an accessibility pass, production
   deploy.

**Follow-up (separate spec)**: import posts, categories, tags and media from
the current WordPress site through its REST API (HTML converted to Tiptap
JSON), and generate the redirect map.
